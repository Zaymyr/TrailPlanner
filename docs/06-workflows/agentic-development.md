# Agentic Development

## Purpose

Use this workflow when an AI agent implements or reviews a production change. It complements [Ship a Feature](ship-a-feature.md) by making the specification, evidence, and human review boundary explicit.

## Key Concepts

- Task packet: the smallest self-contained statement of expected behavior, constraints, non-goals, and acceptance evidence.
- Independent oracle: a test, type checker, linter, build, database constraint, or reviewer that does not merely repeat the implementation's assumptions.
- Small batch: a reversible change with one coherent outcome and a reviewable diff.
- Risk-based review: auth, RLS, payments, migrations, destructive operations, and production workflows always require explicit human review.
- Single-worktree default for sequential work: agents switch task branches in the primary checkout so unfinished work remains visible to the maintainer.
- Parallel work: several agents may run at once when each owns a registered worktree, a `dev/*` branch, and a claimed file scope that overlaps no other active claim (see [Parallel agent work](#parallel-agent-work)).
- Model tiers: light, standard, strong, and exceptional roles are defined once in root `AGENTS.md` and mapped to `.codex/agents/` (Codex) and `.claude/agents/` (Claude Code; the exceptional architect runs on `fable`).
- Canonical entry point: every assistant starts from root `AGENTS.md`; vendor-specific files are pointers, not independent rule sets.
- User-owned working state: modifications and untracked files present before the task are preserved and excluded from the task unless the user explicitly says otherwise.
- Stable web integration: web-affecting agent work is developed on `dev/*`, validated after integration into `preview/web`, and only then proposed for `main`.

## Steps

1. Read root `AGENTS.md`, then run `git status --short --branch` before any fetch, branch switch, edit, file generation, or dependency installation. Preserve all pre-existing changes. Never stash, clean, reset, discard, overwrite, or commit them without explicit user approval. If they make the mandatory new task branch unsafe, stop and ask.
2. Write the task packet before editing:
   - user-visible outcome;
   - non-goals;
   - business and security invariants;
   - affected web, mobile, database, and integration surfaces;
   - acceptance checks and rollback path.
3. Read `docs/AGENTS.md`, the closest implementation, its direct imports, its nearest tests, and the routed domain docs.
   Work in the primary checkout for sequential work. For parallel agents, follow [Parallel agent work](#parallel-agent-work) before the first edit.
4. Search for an existing component, helper, policy, RPC, or workflow before adding a new pattern.
5. Split work into independently verifiable changes. Use a disabled feature flag when incomplete work must be integrated.
6. Add or update tests that exercise observable behavior and failure paths. Tests generated by the implementing agent are evidence, not the sole oracle.
7. Run targeted checks during development, then the repository `verify` gate before handoff. For documentation-only work, run documentation/link checks and explain why the full application gate was not necessary.
   For any change affecting the Vercel web inputs, verification evidence also includes the stable deployment created from the long-lived `preview/web` branch. An agent must not use `preview/web` as its task branch or claim production readiness from a disposable feature-branch Preview alone.
8. Review the diff for unrelated changes, exposed secrets, weakened authorization, silent error handling, and documentation drift. Compare the final status with the preflight status so user-owned changes stay excluded.
9. Require a human approval for the high-risk paths listed above before production promotion.
10. Before any push to `main` or production promotion, audit every registered worktree and local-only commit as required by [Ship a Feature](ship-a-feature.md). Treat any dirty worktree or unpushed commit as a release blocker; CI cannot discover uncommitted local files.
11. Hand off with the task branch, changed files, checks run and their results, unresolved risks, and the list of pre-existing changes that were preserved.

## Parallel agent work

Parallel agents are allowed when their file scopes do not overlap. The scope is a list of files, directories, or globs claimed before the first edit and checked again before handoff by `scripts/agent-scope.mjs`. The registry is stored in the shared Git directory (`<git-common-dir>/agent-scopes/`), so every worktree sees the same claims and nothing is committed.

1. The orchestrating agent (or the user) splits the work and writes one task packet per agent, including the file scope it owns. Prefer narrow scopes (specific files or feature folders) over app roots.
2. Each agent gets its own worktree and branch from the latest `origin/main`, then runs `npm install` there before any check:

```bash
git fetch origin
git worktree add ../TrailPlanner-<task> -b dev/<task> origin/main
```

   Claude Code subagents launched with worktree isolation live in `.claude/worktrees/` (gitignored); they must still create or switch to a `dev/<task>` branch before editing. Only one agent writes in a given worktree; the primary checkout counts as one.
3. Before the first edit, claim the scope from inside the worktree:

```bash
node scripts/agent-scope.mjs list
node scripts/agent-scope.mjs claim <task> apps/mobile/components/racebook/ "apps/mobile/app/(app)/plans.tsx"
```

   `claim` fails when the scope overlaps an active claim, or when the worktree already hosts another task. On failure, do not edit the contested paths: ask the user whether to wait, narrow the scope, or serialize the tasks.
4. If the task needs another path mid-way, run `node scripts/agent-scope.mjs extend <task> <path>` before touching it. An overlap there means stop and report.
5. Before handoff, run `node scripts/agent-scope.mjs verify <task>`. It lists every changed code file outside the claim and fails on any, then prints the docs the branch touched so they can be reconciled.
6. Integrate branches one at a time (strong tier or user). After each merge, reconcile every doc edited by more than one branch so it describes the combined behavior, rerun `npm run docs:check`, and rerun the verification gate. Then release the claim with `node scripts/agent-scope.mjs release <task>` and remove the worktree once its branch is pushed or merged.

Rules:

- `docs/` is never claimable. Shared docs (for example `docs/01-architecture/mobile-app.md`) are referenced by many code paths, so each branch updates what its code requires under the documentation maintenance protocol and the overlaps are resolved at integration, not prevented.
- Exclusive groups are reserved as a whole when a claim points inside them: dependency manifests and lockfiles, `supabase/migrations/**`, `packages/design-system/src/tokens/**`, agent instruction files (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`, `.codex/**`, `.claude/agents/**`), and CI/deployment config. A broad claim such as `apps/mobile/**` does not reserve them, and `verify` rejects changes to an unreserved group member. Two agents can therefore never add migrations or change dependencies at the same time.
- Claims prevent textual collisions only. A change to a shared type, contract, or business rule can still break another branch semantically; the integration verification gate is what catches it.
- `node scripts/agent-scope.mjs prune` drops claims whose worktree no longer exists; `list` marks them as stale.
- The release worktree audit of [Ship a Feature](ship-a-feature.md) still applies to every parallel worktree.

## Validation

- Run `npm run docs:check` to verify the `related_files` protocol for local changes.
- For parallel work, run `node scripts/agent-scope.mjs verify <task>`; for changes to the scope tool itself, run `node --test scripts/agent-scope.test.mjs`.
- Run `npm run verify` before requesting review.
- Confirm every acceptance criterion has observable evidence rather than relying on the agent's narrative.
- For database changes, verify migrations from a clean local state and run the relevant SQL checks.
- For UI changes, validate the actual interaction and accessibility path; source-text assertions alone are insufficient.

## Agent Evaluation

Track agent effectiveness with repository outcomes, not generated code volume:

- first-pass verification rate;
- human review and rework time;
- escaped regressions and rollbacks;
- median diff size and lead time;
- flaky-test rate;
- cost per accepted change.

Keep a small set of historical, representative tasks for comparing instruction or model changes. Do not use production secrets or live destructive operations in that evaluation set.

Keep `.github/CODEOWNERS` aligned with release definitions as well as application boundaries. GitHub workflows, Supabase, `apps/mobile/eas.json`, and mobile EAS workflows are maintainer-owned review surfaces.

## Do Not

- Do not accept an agent-authored test as proof when it asserts implementation details instead of behavior.
- Do not broaden scope merely because nearby cleanup is easy to generate.
- Do not hide sequential agent work in auxiliary worktrees.
- Do not let two agents write in the same worktree, or edit a path claimed by another task.
- Do not add `docs/` paths to a scope or skip doc reconciliation when integrating parallel branches.
- Do not repair migration history automatically to hide drift.
- Do not publish an OTA, deploy a migration, or promote production from a commit that has not passed the required verification gate.
- Do not bypass the `preview/web` integration gate for a change that affects the web deployment inputs.
- Do not use line count, commit count, or pull-request count as the primary productivity measure.
- Do not let assistant-specific instruction files duplicate or override the canonical root `AGENTS.md` rules.
- Do not claim a clean handoff without distinguishing task changes from pre-existing working-tree state.
