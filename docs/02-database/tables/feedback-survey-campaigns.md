# feedback_survey_campaigns Table

## Purpose

One row per feedback survey an admin sends from "Messagerie > Questionnaires". A campaign targets an audience (every identified runner who opened one event's livret coureur, or one chosen account for a test send), and each recipient gets one `user_notifications` row with `kind = 'feedback_survey'`. Answers live in [feedback_survey_responses](feedback-survey-responses.md).

## Key Concepts

- Audience kind `racebook_readers`: runners whose PostHog `racebook opened` events carry `properties.event_id = audience_event_id`. Only distinct ids that are Supabase Auth UUID v4 count (PostHog anonymous ids are UUID v7), PostHog internal/test persons and `role = admin` persons are dropped, then `resolve_feedback_survey_recipients` keeps live Auth accounts without the trusted `app_metadata` admin role.
- Audience kind `single_user`: one account picked by the admin (search by e-mail/id, or "M’envoyer à moi") to test a survey before a real send. PostHog is skipped; `resolve_feedback_survey_single_recipient` keeps only a live Auth account and, unlike the audience resolver, allows admins. `audience_event_id` is optional (it only prefills the copy) and `audience_label` reads `Test · <email>[ · <event>]`.
- The campaign id is generated by the admin form and kept across failed retries. Each recipient's notification id is derived from `(campaign id, user id)` (`surveyNotificationId`), so a retried send never duplicates a message.
- The in-app message is mandatory; push (on by default) and Resend e-mail are opt-ins delivered with the same path as admin messages (`deliverAdminUserNotification`).

## Columns

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid | Primary key, chosen by the admin client for idempotency. |
| `created_by` | uuid nullable | Admin who sent it; set null when deleted. |
| `title` / `body` | text | Message copied into each recipient's notification (1–160 / 1–4000 characters). |
| `audience_kind` | text | `racebook_readers` or `single_user`. |
| `audience_event_id` | text nullable | Required for `racebook_readers`: the `race_events` id stored in PostHog `event_id`. Plain text, no foreign key (analytics id). |
| `audience_user_id` | uuid nullable | `single_user` only (check constraint): the targeted account. References `auth.users(id)`, `on delete set null`. |
| `audience_label` | text nullable | Event name, or `Test · <email>` for a single-user send, shown in the admin results. |
| `email_requested` / `push_requested` | boolean | Channels chosen at send time. |
| `recipient_count` | integer | Recipients resolved at the first send. |
| `created_at` / `updated_at` | timestamptz | Creation and trigger-maintained update times. |

## Related Columns On user_notifications

`user_notifications.survey_campaign_id` references this table (`on delete set null`). A non-null value requires `kind = 'feedback_survey'`, and the partial unique index `(survey_campaign_id, user_id)` lets a campaign reach each runner only once.

## RLS Policies

RLS is enabled with no client policy: `anon` and `authenticated` have no privilege. Only `service_role` (admin web routes after `requireAdminAuth`) reads and writes.

## Functions

- `resolve_feedback_survey_recipients(uuid[])` — `SECURITY DEFINER`, service-role only. Returns `user_id`, `has_email`, `has_push` for live Auth users among the ids, excluding `raw_app_meta_data.role = 'admin'`.
- `resolve_feedback_survey_single_recipient(uuid)` — `SECURITY DEFINER`, service-role only. Same columns for one live Auth user, admins included (the admin chose this account explicitly).
- `feedback_survey_campaign_stats(uuid[])` — service-role only. Per campaign: recipients, read count, push sent, responses and "useful" answers (keeps counts exact beyond the Data API's 1000-row cap).

## Gotchas

- The audience comes from PostHog at send time: the server needs `POSTHOG_API_KEY` (personal key with query read access), `POSTHOG_PROJECT_ID` and `POSTHOG_API_HOST`, the same variables as organizer analytics. Without them the audience routes answer 503/502.
- A test send is its own campaign: its read count and answers do not count toward the later real campaign. The test account can still receive the real campaign only if it belongs to that audience (admins never do).
- Readers without an account cannot be contacted; the admin preview reports reachable accounts, push and e-mail counts before sending.
- Push delivery runs inside the send request (bounded concurrency, `maxDuration` 300 s). A pass cap stops the pending loop if a delivery status write keeps failing; re-sending the same campaign resumes pending rows.
